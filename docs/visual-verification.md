Capture에서 `검토` 태그를 명시적으로 선택한 뒤 원문 `Capture 태그 원문입니다.`를 저장하자, 원문은 그대로 유지되고 Records 목록·태그 필터·태그 사용 현황에 `#검토 1회`가 반영됐다. 태그 현황을 선택하면 해당 태그로 검색이 좁혀졌다. 이어 Capture·이번 달 조건을 이름이 다른 저장 검색 두 건으로 만든 뒤 두 번째 조건의 위로 이동 제어를 실행하자 목록 첫 번째 항목으로 즉시 바뀌었다. 인증 세션의 데스크톱과 375px 전체 화면에서 Capture 태그 입력·빠른 선택, 태그 현황, 저장 검색의 적용·이동·삭제 제어가 겹치지 않고 표시됐다. 마지막으로 검증 Record와 태그 행, 저장 검색 두 건을 사용자 ID와 식별 가능한 원문·이름으로 삭제해 Records·태그 현황·저장 검색의 빈 상태로 복귀했다.

태그 사용 현황의 정렬 규칙은 별도 다중 태그 데이터로 보완 검증했다. `계획` 태그 Record를 저장하고 `검토` 태그 Record를 이어 저장한 뒤, `계획` 태그를 빠른 선택으로 다시 저장해 `계획 2회`가 `검토 1회`보다 더 최근에 사용되도록 만들었다. Records는 `최근 사용순 · 횟수`를 명시하고 `#계획 2회`, `#검토 1회` 순으로 표시했으며, 해당 순서와 버튼은 375px 인증 iframe에서도 읽고 조작할 수 있었다. 최근 사용 시각, 사용 횟수, 태그 이름의 보조 기준 정렬은 순수 함수 테스트로 검증했다. 세 검증 Record는 정확한 원문과 사용자 ID 조건으로 삭제했으며 태그 사용 현황·필터·검색 결과가 빈 상태로 복귀했다.

태그 이름 수정·병합은 실제 독립 Capture Record로 검증했다. 같은 원문에 `업무`와 `일`을 명시적으로 연결한 뒤 Capture의 태그 관리에서 `업무 → 일` 병합을 실행하자 원문은 바뀌지 않았고, `업무` 태그는 후보·검색·목록에서 사라지며 이미 존재하던 `일` 연결 하나만 남았다. 서버 mutation 테스트로는 원본 태그가 인증 사용자의 것이 아닐 때 거부되고, 병합된 Record 연결 및 변경 History가 사용자 범위로 처리됨을 확인했다.

Capture 임시저장은 실제 인증 세션에서 검증했다. 원문을 입력하면 `이 기기에서 임시저장 중`과 명시적 비우기 제어가 나타났고, Capture 화면을 다시 열어도 입력 원문이 그대로 복원됐다. `임시저장 비우기`를 실행하면 로컬 초안만 빈 상태로 전환됐으며 기존 저장 Record에는 영향을 주지 않았다.

Today 저장 검색 진입은 `일` 태그 필터를 `[검증] Today 일 태그`로 저장해 검증했다. Today의 `바로 찾기`에 해당 이름이 표시됐고, 이를 선택하자 Records가 저장 검색 ID와 함께 열리며 `#일` 필터 및 원문 한 건이 복원됐다. 저장 검색과 검증 Record는 사용자 ID·정확한 이름·원문으로 삭제해 Today 바로 찾기, 태그 현황, Records를 기본 빈 상태로 정리했다.

Project·Stage·Task 일괄 정리는 인증된 Projects 화면에서 검증했다. `[검증] 일괄 보관 Project`를 만든 뒤 일괄 보관 Project 선택에서 해당 항목만 명시적으로 선택해 실행하자 활성 목록에서 사라지고 삭제 없이 보관 상태로 바뀌었다. 서버 테스트에서는 선택한 사용자 소유 Project·Stage·Task만 각각 보관·취소 상태로 변경하며 History 세 건을 남기고, 타 사용자 Project 선택은 거부함을 확인했다. 375px 전체 화면에서 Capture·Today·Projects·Records의 새 카드와 입력·선택·실행 제어가 겹치지 않고 한 열로 표시됐으며, 최신 브라우저 콘솔에서 새 기능 관련 오류는 확인되지 않았다.

최종 정리에서 보관된 `[검증] 일괄 보관 Project`가 Records와 Capture의 활성 연결 선택지에 남지 않도록 Workspace 조회를 활성 Project·Stage·Task로 제한했다. 인증된 데스크톱 Records와 375px 전체 화면의 Records·Capture·Projects·Today를 다시 확인해 검증 Project 이름이 노출되지 않고, 각 화면이 Record 0개·태그 없음·저장 검색 없음·활성 Project 없음의 기본 상태로 유지되는 것을 확인했다.

상위 Project 보관 후에도 남아 있던 Stage·Task를 추가로 확인해, 활성 Workspace는 활성 Project에 연결된 Stage와 Task만 반환하도록 보완했다. 인증된 데스크톱 DOM에서 Records의 Project·Task 필터는 각각 기본 선택지만, Capture의 Project·Task 선택지는 각각 연결 안 함만, Projects의 Project·Stage·Task 다중 선택지는 빈 목록만 표시했고, Today 본문에도 `[검증]` 이름이 없음을 다시 확인했다.

동일 인증 세션의 375px iframe DOM에서도 네 화면을 재확인했다. Records는 `전체 Project`·`전체 Task`만, Capture는 각 연결 안 함만, Projects는 세 일괄 보관 선택지의 빈 목록을 반환했고, Records·Capture·Projects·Today 본문 모두 `[검증]` 이름을 포함하지 않았다. 전체 화면 캡처에서도 각 카드와 선택 제어가 한 열로 유지되며 겹침이 없었다.

모바일 안정성 보완 후 375×812 전체 화면에서 Today·Capture·Projects를 재확인했다. Today의 Continue·일정·`기록하기`, Capture의 원문·태그·연결·첨부 제어, Projects의 생성·일괄 보관 제어는 한 열을 유지하고 겹치지 않았다. Capture는 네트워크가 끊기면 원문·태그·연결·첨부를 이 기기의 전송 대기함에 저장하고, 재접속 시 같은 요청 식별자로 재전송하도록 구현했다. 서비스 워커는 동일 출처의 정적 자산만 캐시하며 화면 탐색 요청과 사용자 데이터 요청은 캐시하지 않는다. 앱 복귀·재접속에서는 Workspace 데이터를 다시 읽고, 실제 변경이 감지될 때만 다른 기기 변경 반영 알림을 표시한다.

다중 기기 수정은 Project·Stage·Task·Schedule의 수정 버전으로 보호한다. 오래된 화면에서 저장하면 최신 저장값과 내 입력값을 비교해 보여 주고, 사용자가 명시적으로 다시 적용하거나 최신값을 유지할 수 있다. Projects에는 보관함·복원 제어와 보관 History를, 데이터 내보내기에는 사용자별 Project·Stage·Task·Record 원문 Markdown 및 Records CSV를 추가했다. 실제 Capture에서 `원복검증-원본 → 원복검증-대상` 병합 뒤 최근 병합의 `되돌리기`를 실행해 원본 태그 복원과 Record 원문 보존을 확인했다. 검증 Record·History·병합 스냅샷은 정확한 사용자 ID·원문·태그 조건으로 삭제해 기본 상태로 정리했다.

최종 회귀에서는 오래된 Project·Stage·Schedule 수정 버전이 서버에서 거부되고 현재 저장값을 덮어쓰지 않는 mutation 테스트를 확인했다. 충돌 안내 컴포넌트는 최신 저장값·내 변경·`내 변경 다시 적용`·`최신값 유지`를 포함하는 접근 가능한 alert로 서버 렌더링 테스트를 통과했다. 동기화 비교 로직, 설치형 앱 매니페스트·정적 자산 캐시 정책, Markdown·CSV 원문 보존 형식도 각각 단위 테스트로 확인했다. 이후 인증된 375px Projects 화면에서 빈 보관함·내보내기·활성 Workspace 빈 상태가 겹침 없이 한 열로 유지되는 것을 확인했다.
